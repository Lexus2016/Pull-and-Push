## H1 (ПІДТВЕРДЖЕНО) — немає звірки назв метрик onboarding із контрактом движка

### Доказ (ланцюг даних)

1. `bot_engine.simulate` друкує ЖОРСТКО фіксований набір ключів:
   `return_oos_pct`, `liquidations`, `max_drawdown_pct`,
   `max_drawdown_bars`, `full_max_drawdown_pct` (+ report-only).
   Це і є реальний скорер onboarding (через `score-bot`).
2. `profile_schema.ExtractableFact.name` — довільний рядок, який ВИГАДУЄ
   LLM-аналізатор (приклади в коментарі: "return" | "sharpe" | "drawdown").
   Не прив'язаний до жодного контракту.
3. `proposer.ground_proposal` відкидає метрики, яких нема в
   `profile.extractable_metrics` — тобто звіряє «proposal проти profile»,
   а НЕ «proposal проти реальних ключів simulate()».
4. Отже між profile → proposal → config немає жодної точки, де назви
   метрик звіряються з фактичним виходом движка.

### Наслідок

Якщо аналізатор/proposer назве метрику `sharpe`, `drawdown`,
`max_drawdown_days` чи будь-що поза 5 ключами движка — `ground_proposal`
її пропустить (вона ж є в профілі, який та сама модель і вигадала),
конфіг створиться валідним. На першому прогоні `numeric`-адаптер не
знайде метрику в JSON → гілка `missing` в orchestrator → verdict `fail`
щоітерації до `plateau_N` → прогін тихо вмирає, паливши токени на агентів,
нічого не оптимізувавши. Користувач бачить миттєвий «finished plateau»
без пояснення першопричини.

### Споріднена менша невідповідність (шаблон)

`templates/btcusdt-futures/template.json` скорить `max_drawdown_days`,
і його harness `run_backtest.py` реально її друкує — тут узгоджено.
Але `bot_engine.simulate` для ТОГО Ж домену друкує `max_drawdown_bars`.
Два шляхи коду (шаблонний backtest vs onboarding-движок) мають різні
контракти назв для однієї суті. Це не баг сам по собі, але підвищує
ризик H1: користувач, бачивши шаблон, природно назве `max_drawdown_days`
при onboarding — і потрапить у пастку.

### Варіанти виправлення H1 (рішення за власником — НЕ виправлено в межах аудиту)

- Варіант A (запобіжник, рекомендований): у `scaffold_onboarding` /
  `build_onboarding_config` звіряти `proposal.proposed_metrics` проти
  фіксованого набору ключів, що друкує `bot_engine.simulate`. Невідповідні —
  відхиляти з явною помилкою (як `_assert_scorer_exists` для скорера).
  Дешево, ловить пастку до створення проєкту.
- Варіант B (документування): додати дозволений набір назв у промпт
  proposer'а та в коментар схеми. Слабше — покладається на слухняність LLM.
- Варіант C (ґрунтовно): зробити перелік `simulate()`-ключів єдиним
  джерелом істини (константа), на яку посилаються і engine, і валідація,
  і шаблон. Усуває і споріднену невідповідність days/bars.

Моя рекомендація: A зараз (закриває діру), C згодом (усуває клас проблем).
Я свідомо НЕ вношу правку: задача була аудит (діагностика), а у H1 є
дизайн-вибір, що належить власнику. Готовий реалізувати будь-який варіант
за окремим запитом.

## H2 — Docker-скорер не валідовано в CI; local-бекенд без ізоляції

Визнано в коді (`sandbox.py`) і SECURITY.md. `DockerBackend` реалізовано,
але живий запуск контейнера не перевіряється в CI (нема daemon у dev-боксі).
Дефолт `local` виконує згенерований LLM код БЕЗ ізоляції на хості. Для
unattended/недовірених прогонів — перевірити docker на реальному хості
перед використанням. Найслабша ланка моделі безпеки на практиці.

## H3 — WebUI auth = токен у query-параметрі URL

`/api/...?token=<value>`. Токен тече в логи, історію браузера, Referer.
Нема CSRF, нема multi-user. Для localhost single-user прийнятно (заявлений
сценарій, чесно задокументовано в SECURITY.md). Будь-яка експозиція назовні
без TLS-reverse-proxy = ризик. Окремо: `/api/fs` лістить будь-яку теку
сервера (лише імена) — для локального інструмента ок, при експозиції — обхід.

## Сильні сторони (зроблено правильно — варто зберегти)

- Anti-collusion за дизайном: scorer/referee — детермінований код, ніколи
  не LLM; harness фізично поза artifact-текою, невидимий executor'у
  (`_artifact_snapshot` виключає harness_dir).
- Git як джерело істини: «змінив агент щось чи ні» вирішує `git status`.
  Кандидат комітиться до скорингу; side-effects скорингу відкидаються.
- Re-baseline при зміні objective: вся історія перескорюється на нову
  шкалу, з логом — не мовчазне переписування.
- Whole-period drawdown gate: закриває exploit «злив in-sample заради
  роздутого scale-invariant OOS %».
- Anti-look-ahead probe: реверс OOS-хвоста — каузальний скор мусить
  відреагувати; елегантна перевірка на витік майбутнього.
- Bot protocol без timestamp: бот не може зафінгерпринтити діапазон дат.
  Прихований seeded OOS-split.
- Обробка підпроцесів: process groups для Force-Stop, watchdog проти
  write-stall deadlock, bounded I/O (1MB cap), PTY для live-логів з ANSI-стрипом.
