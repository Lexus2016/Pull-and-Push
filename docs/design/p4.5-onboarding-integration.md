# P4.5 — Onboarding integration (turnkey scaffold)

Status: **design + build**. Closes the gap P3.3 deferred as "P4+: a turnkey onboarding template
(template.json + scaffold) that bundles harness data + a generated adapter", and is the explicit
precondition for **P5** in [`onboarding-existing-bots.md`](./onboarding-existing-bots.md)
("enabled only once P1–P4 make 'improve what I have' actually work").

## The gap

After P1–P4 a user can `profile` → `propose` → `validate` a bot, but to actually OPTIMIZE it they
must hand-author a `config.yaml` that wires the `score-bot` command, maps the proposal's metrics,
seeds the artifact with the bot, and isolates the data. That manual assembly is the missing
"improve what I have" on-ramp. P4.5 generates it.

## Decision: onboarding is a parametrized scaffold

The existing template scaffold (`scaffold.py`) already lays down a project as:

    <project>/artifact/   the editable surface (executor tunes it; cwd of the eval command)
    <project>/metrics/    the hidden harness — OUTSIDE artifact (executor can't see/edit it; lock #4)
    <project>/config.yaml validated run config

Onboarding is the SAME shape with the parts sourced from the user instead of a fixed template:

- **artifact/** ← copy of `--bot-dir` (the executor tunes the bot's tunables / logic).
- **metrics/data.csv** ← copy of `--data` (the OHLCV series). It lives OUTSIDE the artifact, so the
  bot/executor can neither read the held-out OOS tail nor game it — matches the ADR data-isolation.
- **config.yaml** ← built from the P2 proposal:
  - `evaluation.adapter: numeric`
  - `evaluation.command: "{python} -m tyani_tolkai.cli score-bot --data ../metrics/data.csv
    --bot-dir . --bot-cmd \"<cmd>\" --seed <token>"`
    - cwd is the artifact (numeric adapter runs with `cwd=artifact_dir`), so `--bot-dir .` is the
      LIVE edited bot and `../metrics/data.csv` is the read-only sibling.
    - `{python}` is substituted by the numeric adapter (`_resolve_python`); `-m tyani_tolkai.cli`
      avoids depending on the `pull-and-push` console script being on PATH inside the run env.
  - `evaluation.metrics` ← one `MetricCfg` per `proposal.proposed_metrics` (name, dir, weight,
    target; `worst` left None → baseline-derived by the orchestrator).
  - `sandbox.backend: local` — the orchestrator runs `score-bot` as a plain subprocess; score-bot
    itself spawns the Docker sandbox for the bot. Setting `local` here avoids docker-in-docker.
  - `agents`: executor + validator both `claude` (the works-out-of-the-box default; mixing is a
    one-line edit).
  - `seed.mode: empty` — the bot is copied into the artifact and the first git commit is the
    reset baseline (same as the template path).

## Seed token (hidden OOS split)

`score-bot --seed` fixes the bot-hidden OOS tail (`seeded_oos_start`). It must be stable per project
and unknown to the bot (it is — the bot never sees `--seed`). Default `--seed` = the project name
(deterministic, stable across resumes); overridable via `onboard --seed`.

## CLI

    pull-and-push onboard --bot-dir DIR --data CSV --proposal proposal.json --name NAME \
                          --bot-cmd "python bot.py" [--seed TOKEN] [--goal TEXT]

→ creates the project and prints the next step: `pull-and-push run <project>/config.yaml`.

Exit: `0` ok; `2` bad input (missing bot-dir/data/proposal, invalid proposal JSON, no metrics,
duplicate project name).

## Functions (`scaffold.py`)

- `build_onboarding_config(name, *, proposal, data_rel, bot_cmd, seed_token, goal, harness_dir="metrics")
  -> dict` — pure: assemble + validate (`Config(**cfg)`) the config dict from a `MetricProposal`.
  Raises if the proposal has zero metrics (EvaluationCfg needs ≥1).
- `scaffold_onboarding(name, *, bot_dir, data_path, proposal, bot_cmd, seed_token=None, goal=None)
  -> dict` — lay down artifact (bot copy) + metrics/data.csv + config.yaml; commit seed. Mirrors
  `scaffold_project`. Returns `{created, data, metrics}`.

## The bot must speak the P3 protocol

`--bot-cmd` must launch something that speaks the JSON-lines bot protocol (`bot_protocol.py`:
init→ready, bar→order, end). A raw user bot usually does NOT — it must be wrapped with a thin
adapter that imports the bot's decision logic and exposes it via `run_protocol_io()` (see the
reference `bot_adapter.py`). The wrapper is BOT-SPECIFIC (it depends on the entry point P1 found),
so generating it correctly is per-bot work — deliberately NOT auto-done here. A WRONG adapter would
silently mis-score (the exact failure class this whole milestone exists to prevent), so onboard
wires the project and is explicit that the operator points `--bot-cmd` at a protocol-speaking
command; adapter synthesis is its own step.

## Run-time requirement

The generated run needs Docker available (score-bot scores the untrusted, LLM-mutated bot in the
sandbox). The `onboard` SCAFFOLD step itself needs no Docker and is fully unit-testable; a real
optimization run needs Docker (as the architecture requires).

## Out of scope
The intent-first UI (P5); per-bot adapter synthesis (generating the protocol wrapper from the P1
profile — reference: `bot_adapter.py`); auto-running profile→propose inside `onboard` (kept as
explicit prior steps so the human reviews the profile + approves the proposed metrics first — the
ADR's human gate).
