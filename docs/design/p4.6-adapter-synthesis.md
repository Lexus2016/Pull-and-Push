# P4.6 — Adapter scaffolding + the adapter trust gate

Status: **design + build**. Closes the last backend gap before an *arbitrary* (non-protocol-native)
bot can be onboarded: P4.5 wires the project, but `--bot-cmd` must speak the P3 protocol. This phase
gives the user a scaffolded adapter and — crucially — a gate that PROVES an adapter is sound before
the optimization loop trusts it.

Phase of [`onboarding-existing-bots.md`](./onboarding-existing-bots.md) (the P3.3-deferred
"generated adapter").

## The shape of an adapter (from `bot_adapter.py`)

An adapter is exactly two parts:
1. **`run_protocol_io(stdin, stdout)`** — GENERIC plumbing, byte-identical for every bot
   (init→ready, bar→accumulate→`decide(history)`→order, end→return). Pure boilerplate.
2. **`decide(history) -> int in {-1, 0, 1}`** — BOT-SPECIFIC: calls the user's strategy and maps its
   output to a position (long / flat / short). This is the only part that varies.

So "adapter synthesis" reduces to producing one `decide()` that faithfully calls the user's bot.

## Decision: deterministic template scaffold + a strong gate — NOT blind LLM synthesis

The milestone exists to stop silent mis-scoring. An LLM-written `decide()` that subtly mis-calls the
bot (wrong field, reversed sign, ignores params) would mis-score *silently* — the worst outcome.
So P4.6 does NOT ship a trusted LLM generator. Instead:

- **`gen-adapter`** writes a deterministic `adapter.py` = the vetted `run_protocol_io` boilerplate +
  a `decide()` STUB carrying the P1 profile's entry-point hints (location, inputs, outputs) as
  comments. The human (or, later, the loop's executor) fills the one function. No magic to mis-trust.
- **`check-adapter`** is the trust gate: it drives the adapter through the real protocol on synthetic
  bars and proves it is sound BEFORE `onboard`/`run` depend on it.

This mirrors the ADR's own move for the scorer (vetted engine + gate, not a trusted generated judge).
LLM auto-fill of `decide()` is a possible later enhancement — but only ever behind this gate.

## `check-adapter` — the gate (deterministic, no LLM, no Docker)

Reuses `drive_bot` (bot_runner), which already enforces the protocol: ORDER type, monotonic `n`, and
`want ∈ {-1,0,1}` — any violation raises `BotProtocolError`. The gate adds the sanity checks
`drive_bot` does not:

1. **Well-formed** — `drive_bot` ran without `BotProtocolError`/timeout and returned one order per bar.
2. **Deterministic** — drive twice on the same synthetic bars; the two order lists must be identical
   (a non-deterministic adapter makes every downstream score noise).
3. **Non-degenerate** — orders are not all identical across a *varied* probe series. A `decide()` that
   returns a constant (e.g. an unfilled stub, or one wired to a dead value) is FLAGGED — it is the
   classic "looks wired but isn't" failure. (Reported, not a hard error: a genuinely always-flat bot
   is legal but worth a human's eye.)

Verdict PASS/FLAG; exit `0`=PASS, `3`=FLAG, `1`=adapter error (protocol/timeout), `2`=bad input.

Probe data: `synth_bars(n)` — a deterministic, non-monotonic OHLCV series (rises and falls) so a
direction-sensitive `decide()` actually varies its output.

## What the gate does NOT prove (layered defense — peer-reviewed, agy/Gemini)

A black-box order-stream gate proves PROTOCOL soundness, not SEMANTIC correctness. Cross-check
surfaced four mis-scoring defects that pass well-formed+deterministic+non-degenerate, and where each
is actually caught:

- **Look-ahead / lag** — *structurally prevented* by the vetted `run_protocol_io`: it appends bars
  one at a time and passes `decide(history-so-far)`, so a `decide()` built on the shipped boilerplate
  cannot see the future. (Only deviating from the boilerplate reintroduces it — hence we SHIP it.)
  Belt-and-braces: `validate`'s P4.2 anti-look-ahead probe re-checks at scoring time.
- **Sign reversal** (buy mapped to sell) — invisible to the gate (orders look valid either way),
  caught downstream by `validate`'s control spectrum: a sign-flipped bot loses to `flat`/`random` →
  FLAG.
- **Statefulness loss** — neutralized by the contract: `decide(history)` receives the FULL
  history-so-far every call, so it must be a pure function of that history (rebuild any state from
  it). The stub documents this; a `decide()` honoring it is stateless-correct by construction.
- **Scale mismatch** (dollars vs cents, swapped fields) — invisible to the gate; caught
  probabilistically by `validate`'s controls and ultimately by the human reading the evidence report.

So the trust chain is: **`check-adapter`** (protocol + determinism) → **`validate`** (semantic sanity
via the control spectrum + anti-look-ahead + the human evidence report) → human approval. The gate is
one necessary layer, deliberately not claimed as sufficient. `check-adapter` output points the user
to run `validate` next.

## Functions

- `validation.py`: `synth_bars(n=40) -> list[tuple]` (pure); `check_adapter_orders(run1, run2,
  n_bars) -> dict{well_formed, deterministic, degenerate, ok, reasons}` (pure).
- `adapter_gen.py` (new): `render_adapter_stub(*, profile=None) -> str` — returns the adapter.py
  source (boilerplate + profile-informed `decide()` stub).
- `cli.py`: `cmd_check_adapter` (drive_bot ×2 → `check_adapter_orders` → verdict) and
  `cmd_gen_adapter` (write `adapter.py`, refuse to overwrite without `--force`).

## Out of scope
LLM auto-fill of `decide()` (later, behind this gate); multi-language bots (the boilerplate is
Python); folding `check-adapter` automatically into `onboard` (kept explicit so the human runs the
gate and reads the verdict — the ADR's human checkpoint).
