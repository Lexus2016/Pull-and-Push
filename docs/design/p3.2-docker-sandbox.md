# P3.2 — Docker sandbox (design)

Status: **design**. Implements the sandbox sub-phase of [`p3-scoring-core.md`](./p3-scoring-core.md).
Both cross-AI reviewers (agy/Gemini, opencode) recommended a vetted container/jailer over a
hand-rolled namespaces/seccomp wrapper. Local Docker is available, so the sandbox is built on
Docker and is buildable+testable on this machine (Docker runs the Linux kernel features in its VM).

## Decision

The untrusted bot runs inside a hardened `docker run` container. The engine (parent, on the
host) keeps the held-out data and the scoring code; it talks to the container over the SAME
JSON-lines protocol via the container's stdin/stdout. **The entire P3.1 driver is reused
unchanged** — only the spawned command changes (wrapped in `docker run`) plus container
lifecycle. Anti-look-ahead / anti-exfiltration already live in the protocol (P3.1); Docker adds
the kernel-level escape/exfiltration/resource jail.

## Isolation flags (the actual jail)

`docker run --rm -i --name <uuid>` with:
- `--network=none` — no network at all (kills exfiltration + collusion).
- `--read-only` — root FS read-only; `--tmpfs /tmp:rw,size=16m,noexec,nosuid` only if the bot
  needs scratch.
- `--memory=<MB> --cpus=<n> --pids-limit=<n>` — resource caps (no fork bomb / OOM host).
- `--cap-drop=ALL --security-opt=no-new-privileges` — no Linux capabilities, no privilege gain.
- `--user 65534:65534` (nobody) — non-root in the container.
- `-v <bot_dir>:/bot:ro -w /bot` — ONLY the bot's own directory, read-only. The OHLCV data, the
  held-out split, and the engine code are NEVER mounted — they live on the host and stream as
  bars over the pipe.
- `--pull=never` (use a pre-pulled image) so a run can't fetch arbitrary layers.

Verified on this host: `docker run --rm --network=none --cap-drop=ALL --security-opt=no-new-privileges
python:3.11-slim ...` works; `python:3.11-slim` is pulled.

## Container lifecycle (no leaks)

The container gets a unique `--name`. `--rm` + killing the `docker run` client usually cleans up,
but the daemon owns the container, so the runner ALSO force-removes it in a `finally`
(`docker rm -f <name>`, errors ignored). The P3.1 driver's watchdog + masked errors + bounded I/O
all still apply to the `docker run` client process.

## API

New `src/tyani_tolkai/bot_sandbox.py`:
- `docker_available() -> bool` — `docker version` exits 0.
- `SANDBOX_IMAGE = "python:3.11-slim"` (default; overridable).
- `build_docker_cmd(bot_cmd, *, bot_dir, container_name, image, mem_mb, cpus, pids) -> list[str]`
  — the hardened command list (pure; unit-testable without Docker).
- `score_bot_sandboxed(bot_cmd, bars, *, bot_dir, seed, params, image=SANDBOX_IMAGE, mem_mb=512,
  cpus=1.0, pids=64, per_read_timeout=10.0, total_timeout=120.0) -> dict` — builds the docker cmd
  with a uuid container name; `try:` reuse `bot_runner.drive_bot(docker_cmd, ...)` then
  `bot_engine.simulate(...)` on the seeded OOS split; `finally:` `docker rm -f <name>`. Raises a
  clear error if `docker_available()` is False (never silently run unsandboxed).

`bot_runner.score_bot` stays the trusted-only path (its `allow_untrusted=True` still raises);
`score_bot_sandboxed` is the path that MAY run an untrusted bot, because Docker is the jail.

## Testing

- **Pure unit:** `build_docker_cmd` produces a list containing every required flag
  (`--network=none`, `--read-only`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, the
  memory/cpus/pids caps, the `:ro` mount, the user) — no Docker needed.
- **Docker-gated** (`@pytest.mark.skipif(not docker_available())` so no-docker CI still passes):
  - the reference adapter runs INSIDE the container (mount repo `src` read-only, `PYTHONPATH=/bot`,
    `python -m tyani_tolkai.bot_adapter`) and `score_bot_sandboxed` returns metrics IDENTICAL to
    the non-sandboxed `score_bot` on the same bars+seed (functional equivalence).
  - **network is actually denied:** a one-off `docker run --network=none ... python -c "socket
    connect"` fails — proves the flag works, not security theater.
  - **FS is actually read-only:** a one-off `docker run --read-only ... python -c "open('/x','w')"`
    fails.
  - container is removed after a run (`docker ps -a` has no leftover with our name).

## Out of scope (P3.3+)

- `isolated-bot` `EvaluationCfg` adapter wiring into the orchestrator (P3.3).
- ≥2-run determinism enforcement at config level (P3.3).
- Image provenance/signing, gVisor/Firecracker microVMs (only if the threat model escalates;
  namespace+caps+resource jail via Docker covers the current model).
